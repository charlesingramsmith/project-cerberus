# Derlin (repo: project-cerberus)

A Streamlit app where users log dog sightings and build a "life list" of breeds (like a birding life list). The first sighting of a breed is a **lifer**. Live at https://project-cerberus.streamlit.app. The app's name is **Derlin** (domain `derlin.app`); use it in anything users see. "Cerberus" stays only in code and infrastructure (the `cerberus/` package, `CERBERUS_DEMO`, the repo, the Supabase project, the Streamlit address) until the hosting move. This is a portfolio project, so readable code, tests and the README matter as much as features.

The owner is new to Git and coding. Explain git/deploy steps in plain language and say what each command does.

## Commands (Windows, run from repo root)

```bash
.venv/Scripts/python.exe -m pytest -q                 # run all tests (must pass before commit)
.venv/Scripts/python.exe -m streamlit run app.py      # run locally at http://localhost:8501
.venv/Scripts/python.exe -m pip install -r requirements.txt   # install deps
```

If `.venv` is missing: `python -m venv .venv`, then install the requirements. Python 3.12.

`.claude/settings.json` pre-approves the commands above plus read-only git commands and Supabase `db query`/`db push`, and blocks reading or editing `.streamlit/secrets.toml` (and the Supabase CLI's token folder, see Schema changes). Personal overrides go in `.claude/settings.local.json` (git-ignored).

## Rules and gotchas

- **Never put the Supabase backend in `st.cache_resource` or any shared/global cache.** Each browser session gets its own backend in `st.session_state`; sharing would leak one user's login to another.
- **Deploys and stale code:** Streamlit Community Cloud updates files on a deploy but keeps the running server, which can keep old `cerberus.*` modules (new `app.py` + old helpers = `AttributeError`). The top of `app.py` handles it: `drop_stale_cerberus_modules()` compares `cerberus/*.py` modified times with `cerberus.LOADED_AT` and re-imports if newer, then `refresh_stale_backend()` rebuilds old-class backends in `session_state` (copying their `__dict__`, so users stay signed in). Keep the `cerberus` imports *below* that check, keep `LOADED_AT` in `cerberus/__init__.py`, and give new backend attributes safe defaults in `__init__`. Cached loaders take `file_version(...)` so `st.cache_data` re-reads files a deploy changed (argument names must not start with `_`, or the cache ignores them). If the live app still errors after a deploy: Manage app > Reboot app.
- **Google sign-in:** returning from Google starts a new Streamlit session (empty `session_state`), so the PKCE verifier waits in `cerberus.oauth.PENDING` (server memory, single-use, 10-minute expiry). It must only ever hold verifiers, never sessions or backends. Google refuses to load inside Streamlit Cloud's iframe, and that iframe's sandbox blocks links from navigating the whole tab, so `SAME_TAB_SIGN_IN_JS` makes a click on the `google_sign_in` button navigate the outer (same-origin) page instead; if that fails, the link opens a new tab. Recheck it in a real browser on the live site if Streamlit Cloud changes its wrapper. Supabase **Redirect URLs** must allow `<app url>/**`. `MemoryBackend` fakes the round trip for demo mode and tests.
- **Keep me signed in:** browser `localStorage` holds a single-use Supabase refresh token. **Don't use cookies or `st.context.cookies` for this: on Streamlit Community Cloud the app never receives them** (works locally, fails in production). The component reports what's saved once per page load (`saved` state; reruns the app), then each run `sync_saved_sign_in()` tells it to save the current token, so new tokens from sign-in, a return visit or an hourly refresh are kept; a stale token fails to resume and is deleted. `AppTest` can't run components, so `tests/test_app.py` swaps in a `FakeBrowser`. The component tags its report with the Streamlit session's id (`browser_session`), because an open page can reconnect to a new session that would otherwise reuse an old report holding a spent token. **Keep `auto_refresh_token=False` on the Supabase client:** its default hourly background refresh keeps running on the server after the tab closes and spends the token saved in the browser (refresh tokens are single use), which signs people out. Tokens are swapped only during a run, by `get_session()` inside `refresh_token()` at the top of `sync_saved_sign_in()`, so the new one is saved in the same run. The Google choice travels in the return URL as `?remember=1`. Sign-out uses scope `local` (this device only).
- **Only the publishable/anon key is ever used.** Never add the secret/service_role key to the app. Per-user data isolation relies on RLS, not app code.
- **Sightings are readable by other members** when their owner shares (`profiles.share_sightings`, on by default; RLS policy "Members can read shared sightings"). So any query for *your own* data must filter `.eq("user_id", user.id)` (as `list_sightings` does); don't rely on RLS alone for that.
- **Profiles:** `my_profile()` creates the row on first sign-in from the sign-up username, adding a number if it's taken (`logic.username_candidates`). Usernames are unique ignoring case (`profiles_username_unique` index); Postgres error code `23505` becomes "That username is taken". The app shows `profile["username"]`, not the sign-up metadata name. `profile["avatar"]` is a breed name (shown as that breed's photo by `avatar_html`) or, for older profiles, an emoji from `logic.AVATARS` (shown as a sketched dog: the app shows no emoji). Anything members type is shown to others: render it escaped (`html.escape`) or as plain text, never raw Markdown/HTML. If the profiles table is missing, the app falls back to a stand-in profile and Social says it isn't available. When `my_profile()` creates a profile it sets `backend.profile_is_new` (a class-level default of `False`); the app then shows the `sharing_notice` popup once (`st.session_state.sharing_notice` keeps it open until a button or the X closes it). A widget's browser value beats a changed default, so to change the Settings sharing switch from elsewhere, set `share_switch_to` and let the code just before the toggle copy it into `share_sightings`.
- **Schema changes:** edit `supabase/schema.sql` (keep it idempotent: it's re-run whole every time), add RLS policies for any new table, then apply it with the Supabase CLI: `supabase db query --remote --yes -f supabase/schema.sql` (`--remote` = the linked live project; live changes need `--yes`; CLI v3 is in `%LOCALAPPDATA%\Programs\supabase`, so in Git Bash call it by full path if `supabase` isn't found). For read-only checks add `--read-only`. This changes the **live production database**, so **ask the owner every time** before running it (say what the change does), and never run it from an untested branch's half-finished SQL. Run it before merging code that needs the new schema. If `supabase --version` fails or the project isn't linked, point the owner to `docs/supabase-cli.md` (they run `supabase login`/`link` themselves; never type, ask for or read their access token or DB password) or have them paste the file into the SQL Editor. No `supabase/migrations/` folder: `schema.sql` is the single source of truth. Never run `supabase db reset` against the linked project. `.claude/settings.json` lets `supabase db query`/`db push` run without a prompt (the owner chose this on 26 Nov 2026), so the chat OK above is the only check: get it every time. It still blocks `db reset`, `login`, `link`.
- **Dog profiles and tags:** `dogs` (one row per dog, unique `username` ignoring case, letters/numbers/`.`/`_` only, matching `logic.DOG_USERNAME_RE`) and `sighting_dogs` (tags). Members can read all dogs; only owners change them. Anyone tags any dog, but only in their own sightings. Sightings from both backends carry `dog_ids`; if the tags table can't be read, `SupabaseBackend._tags` returns none rather than failing. `app.py` loads `all_dogs` once per run (`None` = dogs not set up: tagging hides and the old `profiles.dogs` editor shows). `move_listed_dogs_to_profiles()` turns an old `profiles.dogs` list into dog profiles, then empties it. Dog bios are shown with `st.text`. Tapping a tag (`dog_tag_buttons`: tertiary buttons styled as chips by `st-key-dogtag_*` CSS, so Social draws each post in its own `feedpost_<id>` container), "Find a dog" or "See profile page" sets `st.session_state.dog_page`; `dog_page()` is an `st.dialog` drawn at the very end of `app.py` (after the new-member notice, never with it), closed by its X. It shows `backend.dog_sightings(dog_id)`: the same rule as Social (members who stop sharing are left out), with a photo gallery (`.dog-gallery`, `<details>` per photo). A dog can be a cross: `dog_form` has its own "My dog is a cross breed" toggle (`dog_<key>_is_cross`, outside the form) with two listed-breed boxes, and `logic.clean_dog` accepts "A x B" when both are listed (no DB change; `dogs.breed` is plain text).
- **Sighting photos:** optional, via `photo_picker()` in `app.py`: an `st.file_uploader` restyled by `MOBILE_CSS` (`st-key-photo_pick_*`) as one "📷 Add photo" button (phones offer camera or library), then a preview with Change/Remove. It sits *outside* the `st.form` (form widgets only send values on submit, so no preview); it returns the already-prepared JPEG, and `clear_photo(key)` empties it after saving (a counter in the widget key). Used on Spotted! and the dog forms. `logic.prepare_photo` makes a small JPEG with no EXIF (GPS) before `backend.add_photo` stores it in the private `sighting-photos` Storage bucket at `<user id>/<photo id>.jpg` (Storage RLS keys on that first folder, so keep it), then `add_sighting(..., photo_path)`. If the upload fails the sighting is still logged, without the photo. Dog photos live in the same bucket at `<user id>/dogs/<photo id>.jpg`. Who else can see a file is one Storage policy ("Members can see dog and shared sighting photos"): any dog's photo, and photos on sightings the viewer can read (so a member's photos are in Social while they share). `MemoryBackend._may_see_photo` mirrors it. Shown through signed links (`photo_urls`, 1 hour), cached by `photo_links()` in `st.session_state.photo_links` for 50 minutes and fetched only while their tab is open. `delete_sighting` removes the photo too. `AppTest` can't upload files, so app tests add photos through the backend.
- **Spotted! has two steps** (`spot_step` in `st.session_state`): 1 = photo, Photo ID, the cross toggle (`sighting_is_cross`) and the breed picker(s) (`sighting_breed`, `sighting_breed_2`, outside any form), then Continue (`confirm_breed` checks them with `logic.clean_breed` or `logic.cross_name` and stores `spot_breed`); 2 = the photo and breed summary, dog tags, then the `log_sighting` form (name, where, date, post). `fill_from_photo` runs at the end of step 1 (so its spinner shows while the photo is new) and fills step 2's `sighting_date`/`sighting_where`. Both steps are drawn every run inside `spot_step_1`/`spot_step_2` containers and the one not in use is hidden with CSS, because Streamlit drops a widget's value (and an uploaded photo) once it stops being drawn. In `AppTest`, pick a breed, click "Continue", then "Spotted!" (`log_breed` in `test_app.py`). Posting sets `clear_tags`, which resets both steps on the next run.
- **Photo ID:** `photo_id_suggestions()` in `app.py` runs the model once per photo on Spotted! (result cached in `st.session_state.photo_id_result` by the photo's hash) and shows up to 3 rows, each with the breed's own photo (`breed_photo_html`, to compare with the member's photo) and a Pick button; tapping it sets `sighting_breed` (`pick_breed`). The model only suggests; never log a breed without the member's tap. The model is loaded by `load_photo_id()` in `st.cache_resource`: fine because it holds no member data (the backend still must never be cached). If it can't load, the app carries on without suggestions. Thresholds (`LIKELY`, `POSSIBLE`, `MIN_DOG`, `MIN_SHOWN`) are in `logic.py`. A new or retrained model replaces `models/dog_breeds.onnx` and `data/photo_id_breeds.csv` together; keep it small (Streamlit Cloud's free memory). `AppTest` can't upload files, so app tests don't reach Photo ID; `test_photo_id.py` covers it.
- **Date and place from a photo:** `photo_picker` also keeps `logic.photo_details` of the *original* upload (date taken, GPS rounded to ~100 m) in `st.session_state["<key>_details"]`, read before `prepare_photo` strips EXIF. On Spotted! `fill_from_photo()` fills `sighting_date` and `sighting_where` once per photo, only if they're empty/today or still hold an earlier photo's fill. Never store coordinates: only the place-name text the member keeps. Missing details (iOS Safari often strips GPS, screenshots have none) fill in nothing, silently. `AppTest` can't upload, so app tests set `sighting_photo_details` and patch `places.fetch_json`.
- **Verified and unverified breeds:** every breed in `data/breeds.csv` is verified (`listed` in `app.py`). The Spotted! picker (`accept_new_options=True`) also offers member-added breeds and takes typed ones; `logic.clean_breed` matches known names ignoring case. A new one is logged with that name and added to the shared `user_breeds` table (`backend.add_user_breed`; unique ignoring case, a duplicate is fine; if the table is missing the sighting is still logged and `list_user_breeds` returns none). Only listed breeds (and crosses) are lifers or count for badges (pass `listed=`). Unverified ones show an "Unverified breed" chip (`unverified_chip`), and a section on the life list. Verifying = adding the breed to the `data/` breed files with the same spelling. In `AppTest`, the `typing` fixture in `test_app.py` lets a selectbox take a typed value.
- **Cross breeds:** no extra column: a cross is a sighting whose `breed` is "Breed A x Breed B" (`logic.CROSS_SEPARATOR`, built by `logic.cross_name` with the parents in A to Z order so each cross has one name, read back by `cross_parents`/`is_cross`). The "It's a cross breed" toggle (`sighting_is_cross`) sits outside the Spotted! form so the second box (`sighting_breed_2`) appears at once; a Photo ID Pick fills the second box once the first is set. The first sighting of each cross is a lifer while `logic.CROSSES_ARE_LIFERS` is True (the owner chose this on 27 Nov 2026 but may change their mind: flipping it is the whole change, since lifers are worked out from sightings). Crosses count for Lifer badges (and have their own Cross badges) but never for Purebred badges or the "of 141" total; the life list shows **Lifers** (breeds + crosses) next to **Breeds** x/141. Badge celebrations compare earned keys before and after a post (`badges_before`, `logic.newly_earned`). `unverified_breeds` leaves them out and `cross_breeds` lists them (life list **Crosses**). Only a cross's unlisted parents go to `user_breeds`, never the cross. Show them with `breed_chip` ("Cross breed" chip). No breed name may contain " x ".
- **Lifer celebration:** no `st.balloons()`. A new lifer (or cross lifer) flash draws `face_balloons_html()`: the breed's face crop (`breed_photo_html`) in circles that float up with pure CSS (`.face-balloons` in `MOBILE_CSS`, about 2-2.5 s; hidden for reduced motion); a cross takes turns between both parents' faces, and a breed with no photo floats a sketched dog. Positions and timings come from `logic.celebration_layout`.
- **Adding a backend method:** add it to the `Backend` protocol and to **both** `SupabaseBackend` and `MemoryBackend`, with tests for each.
- **Secrets:** `.streamlit/secrets.toml` is git-ignored and holds real keys. Don't read it, print it or commit it. The template is `.streamlit/secrets.example.toml`.
- Supabase auth errors are wrapped in `AuthError`; the UI shows `str(err)`. Data calls that raise `AuthError` (expired session) send the user back to sign-in via `end_session()`.
- `AppTest` widgets are found by `key=` (e.g. `sign_up_email`). Give new form inputs explicit keys.
- Dates are stored and compared as ISO strings (`YYYY-MM-DD`). The Social feed is ordered by `created_at` (when posted, set by the DB; `MemoryBackend` stamps it too), not `seen_on` (which a photo can set earlier); `logic.posted_on` gives the day in the member's browser time zone (`st.context.timezone`).
- **Feature votes:** `feature_votes` RLS hides other users' rows, so totals come from the `feature_vote_counts()` security-definer function (counts only, never who voted). A vote's `feature` is `logic.feature_key()` of the roadmap item's bold title. Suggestions land in `feature_suggestions`; the owner reads them in the Supabase Table Editor. If those tables are missing, Settings shows "Voting isn't available" instead of crashing.
- **New-update dot:** the main tabs use `key="main_tab", on_change="rerun"`, so switching tabs reruns the app and `st.session_state.main_tab` holds the open tab's label. Opening Settings calls `backend.mark_version_seen()`; Supabase stores it as `seen_version` in the user's `user_metadata` (no table). All tabs still render every run, so tests can read every tab; in `AppTest`, switch tabs by setting `at.session_state["main_tab"]` to a label and running.
- **Mobile first.** Design for a ~375px phone, then check desktop. Avoid `st.sidebar`, `st.columns` for side-by-side items (they stack on phones; use `st.container(horizontal=True)`) and wide `st.dataframe`s (use list rows or bordered cards). Buttons that end a form use `width="stretch"`.
- **No HTML tags inside `<style>` blocks given to `st.html`, not even in CSS comments**: the sanitiser silently drops the whole stylesheet (`test_page_styles_contain_no_html_tags` guards this).
- `MOBILE_CSS` targets Streamlit internals (`data-testid`, `.st-key-<key>` classes, `role="tablist"`), which can change when Streamlit is upgraded: recheck the phone layout after bumping the version. The bottom tab bar (`main_nav` container, labels in `NAV_TABS`, each with its hand-drawn icon from `NAV_ICONS` in the same order) is pinned on all screen sizes; its colours must match `[theme.light]`/`[theme.dark]` `backgroundColor`. Below 840px wide the tabs are lifted 3rem so Streamlit Cloud's bottom-right badge (outside the app's iframe, can't be styled) doesn't cover Social/Settings; recheck on the live site if the badge changes size. That lift (`STREAMLIT_CLOUD_BADGE_CSS`) is only added when `logic.on_streamlit_cloud(st.context.url)`, so Render has none; delete it once the Streamlit Cloud app is retired.
- **Brand colours:** pastel pistachio (`primaryColor`) with plum highlights. They're set in `.streamlit/config.toml` and as CSS tokens (`--ink`, `--pistachio`, `--plum`, ...) at the top of `MOBILE_CSS` (light) and in `DARK_CSS` (dark); change them together. Pastel pistachio is too pale for Streamlit's white button text, so `MOBILE_CSS` gives primary buttons dark text and uses a deeper green for the open tab and selected options; keep that for any new primary-coloured element. Use the tokens, not hex colours, in new CSS.
- **No emoji in the app.** Use a hand-drawn icon from `cerberus/sketches.py` (add one if needed) or plain words; widget labels (buttons, expanders, alerts) can't hold icons, so they're plain text.
- **Light and dark mode:** light by default, with a "Dark mode" switch in Settings > Appearance. Streamlit has no public way to change theme from code, so the saved-sign-in component (`cerberus/remember.py`) finds the switcher Streamlit's own menu uses by walking React's internal tree from `[data-testid="stApp"]` (`streamlitThemes()`, themes named "Custom Theme Light"/"Custom Theme Dark") and calls it: instant, no reload, and Streamlit saves the choice under `stActiveTheme-<path>-v2`. **Recheck the switch after every Streamlit upgrade**: if that internal moves, it falls back to saving the key and reloading the page, carrying the sign-in over the reload once in `sessionStorage` (`carry`, used by `resume_saved_sign_in`). A first visit switches to light the same way. The theme the page loaded with comes in the component's first report (`st.session_state.theme`); the switch then sets it directly. In dark, `DARK_CSS` swaps the brand colour tokens and tab bar colour. Don't use `prefers-color-scheme` in CSS: the phone's setting no longer decides.
- To check the phone layout: the `cerberus-demo` entry in `.claude/launch.json` runs demo mode on port 8502; view it at 375px wide in light and dark.

## Workflow

- **Pushing to `main` deploys to production** (Streamlit Community Cloud redeploys automatically). Run the tests before every push. Merge a branch into `main` only once it's tested.
- **One session, one branch.** At the start of every session, before editing anything, check `git status` and create a new branch for the task, named after it (e.g. `photo-upload`), from an up-to-date `main`: `git fetch` then `git switch -c <name> origin/main`. If the folder has uncommitted work from another branch, don't switch or stash it (another session may own it): make a separate folder with `git worktree add ../project-cerberus-<name> -b <name> origin/main` and work there. Tell the owner which branch you made and why. Only skip this if the owner says to continue on the current branch.
- Commit messages: an imperative summary line, e.g. "Add photo upload to sightings", then a blank line and **always** a short plain-English explanation of what changed and why (a few lines a non-coder can follow). No summary-only commits, even for small changes.
- **Keep this file current, unprompted.** Before every commit, check whether the change makes anything here wrong or missing (new files, commands, rules, gotchas). If so, update CLAUDE.md in the same commit. Keep it short and accurate; don't log history here (that's what git is for).
- Git commits use the owner's GitHub noreply email (already configured globally). Don't change git config.
- Keep `README.md` up to date (features, roadmap, architecture) when features change; it's the project's shop window.
- **Version every user-visible change.** Add an entry at the top of `CHANGELOG.md` in the same commit: `## <version> - <YYYY-MM-DD> - <title>` then `- ` bullets written for users. New feature bumps MINOR (0.6.0 → 0.7.0), fix bumps PATCH (0.6.0 → 0.6.1). `test_logic.py` checks the format and that versions go down the file in order.
- When dependencies change, pin exact versions in `requirements.txt` (Streamlit Cloud installs from it).

## Roadmap

`ROADMAP.md` is the source of truth for planned work (Done / Now / Next / Later / Ideas, with approach notes). Read it before starting a feature. When a feature lands, tick it there and update the README's short roadmap summary in the same commit. The top-level lines under **Now** and **Next** are shown to users in the app (with +1 votes keyed to each bold title), so keep them user-readable and avoid renaming titles casually. The big theme is identifying a dog with ML, like Merlin for birds: photo ID, then sound ID. The model only suggests; picking the breed yourself always stays available.
